# SMILE

Art installation. A camera watches the visitors; when a face holds still in front of it, the image
flashes and ComfyUI paints a portrait of that face, which then grins. The result is shown on the main
screen with music (a Max patch, driven over OSC) and lights (an Art-Net ring around the camera). Two
walls of screens, a sphere of 48, show the grins of the visitors before.

Runs on one Windows PC: an RTX 4090 (24 GB) with 64 GB RAM, an Allied Vision Mako G-125C GigE camera
on the PC's Ethernet adapter, the show monitor and two wall monitors (Datapath units), an Art-Net node for the
lights, and Max for the music. SMILE is `apps\smile` of the Poser2 repository: the commands below run from the
Poser2 root with its `.venv`, and the paths are relative to `apps\smile` unless they start with `apps\`. Everything the installation is given lives in `data\` (presets,
models, workflow, audio, test photos); everything it makes goes to `output\` (clips, portraits, ComfyUI's logs;
not in git, safe to delete); the app's own logs are in Poser2's `logs\`.

### Install script (app, ComfyUI, models)
* in a terminal run Poser2's ```scripts\install.bat``` (the LFS files, the shared `.venv` from `uv.lock`), then ```apps\smile\scripts\install.bat```: it checks ffmpeg, installs ComfyUI in `apps\smile\ComfyUI\` (`scripts\install_comfy.ps1`: ComfyUI core at the commit and the node packs at the versions pinned in `data\comfy\comfy.lock`, the packs from their archives in `data\comfy\packs`, our node pack `data\comfy\aiia_grin` as a junction, the venv from `data\comfy\requirements.lock`), puts the models in place (below) and ends with a smoke test: ComfyUI started once from its venv, on CUDA, and the warm-up run through it
* safe to run again: everything in place is skipped, so a second run is the check of an install; "Install complete" means every step passed. It refuses to run the smoke test while a ComfyUI is on port 8188 (close it first)
* **models**: they live in `ComfyUI\models`, as ComfyUI has it. `data\comfy\models.json` lists every file (path, size, sha256, source); `install.bat` asks for a folder to copy them from, your backup's `ComfyUI\models` or a USB stick (or ```apps\smile\scripts\install.bat --mirror E:\SMILE\ComfyUI\models```), copies and verifies what that folder holds and fetches the rest from the file's source: its public page on Hugging Face (verified by hash, resumed after an interruption), or for the three LoRAs that exist nowhere else their copy in `data\comfy\loras` (git LFS, so a clone has them). About 17.5 GB when everything is downloaded
* **backup**: copy the Poser2 folder. It holds the repo, `apps\smile\ComfyUI\` with its venv and models, and `apps\smile\output\`; a new PC either gets that copy or a clone plus the two install scripts, `apps\smile\scripts\install.bat` pointing at the copy's `ComfyUI\models`
* the model tool on its own, from the Poser2 root: ```.venv\Scripts\python -m apps.smile.comfy.models check``` (every file ok / missing / wrong size / corrupt, and the extra files in the folder), ```install [--mirror DIR]```, and after a model change: ```hash --write``` (the files in the folder into the manifest; ```--add PATH``` for a new one) and ```sources``` (the public pages still hold the same files)
* SMILE runs the API export of the workflow in `data\comfy\smile_workflow.json` and fills in every value from its panel (re-export with **Export (API)** after changing the workflow in ComfyUI); `data\comfy\warmup.jpg` is the photo of the warm-up run SMILE does after every connect, so the models are loaded before the first visitor
* a model the panel names that ComfyUI does not offer is a `WARNING` in the SMILE log, once per file (the workflow's own file runs instead); `start_comfy.bat` starts ComfyUI with `HF_HUB_OFFLINE=1`, so a model that is missing is an error in the ComfyUI log and never a download of whatever is current
* **updating** ComfyUI and the packs, first on the dev PC and never on the installation during a show: ```powershell -ExecutionPolicy Bypass -File apps\smile\scripts\install_comfy.ps1 -Update``` takes the picture of the install as it is (a fixed-seed portrait and grin frame into `output\smoke\before`), renames `apps\smile\ComfyUI\` to `ComfyUI-previous\`, builds a new one with ComfyUI at its newest commit (`-ComfyCommit SHA` for another), every pack at the registry's latest version (its archive downloaded into `data\comfy\packs`) and the venv from their own requirements (not the lock), copies the models over from the previous install, smoke-tests it and saves its picture into `output\smoke\after`. Compare the two folders, then ```install_comfy.ps1 -Accept``` (writes `data\comfy\comfy.lock` and `data\comfy\requirements.lock` from the new install and deletes the previous one; commit the locks and the new archives in `data\comfy\packs`, `git rm` the old ones) or ```install_comfy.ps1 -Rollback``` (the previous install comes back, the locks were never changed). An update may change what a node expects (QwenVL 2.3 added a required input): the smoke test then refuses the workflow and names the node, and the fix is in `comfy\workflow.py`, where the per-run values are filled in, or a re-export of `data\comfy\smile_workflow.json` from the page; nothing in ComfyUI or a pack is edited. The installation then gets the update with `git pull` and the two install scripts.
* no pack is patched: `data\comfy\patches` is empty (the installer still applies what it finds there, as a stopgap for a future pack bug); what SMILE needs from a pack that the pack does wrong is done in `data\comfy\aiia_grin` (Grin Frames builds its own paste mask). The packs' archives are in the repo (`data\comfy\packs`, git LFS), so an install needs neither the Comfy Registry nor the packs' GitHub pages

### Music (Max)
* install Max (Cycling '74); the patch is `data\audio\Smile-Music-Player.maxpat`
* the music (`data\audio\SMILE-BS-Music\`) and the laughter samples (`data\audio\laughter\`) are in git LFS and come in with the models (Poser2's `scripts\install.bat`, or `git lfs pull`); `data\audio\music_map.json` maps the two movements (`0000` for style A, `0001` for style B) to the tracks and their weights
* SMILE sends OSC to Max on `127.0.0.1:4114` (`/music_id`, `/state`, `/progress` and the controls below; the OSC card of the panel's Audio tab); the walls send `/bang <cell>` on 4115 (wall 1, screens 1-24) and 4116 (wall 2) when a clip starts in a cell
* the panel's Audio tab holds the Max panel's controls: `sound` (the patch's DSP), `music_volume` and `laughter_volume` (both dB), `laughter` (the samples those `/bang`s trigger) and `laughter_offset` (degrees, see the speakers below); SMILE sends them every frame (`/sound`, `/music_volume`, `/laughter`, `/laughter_volume`, `/laughter_offset`), so the patch's own controls show them and only work on their own while SMILE does not send (the patch loads with sound and laughter on, laughter level 0 dB); the speaker button in Max holds a click until the panel's `sound` changes
* laughter off: no new laugh starts and one that plays fades out
* **three speakers** on the PC's Realtek jacks: the two beside the camera (60° left and right of it) get the music in stereo and the laughter, the one opposite (180°) laughter only. Windows: Win+R → `mmsys.cpl` (the old Sound panel; also Settings → System → Sound → Advanced → More sound settings; the Windows 11 Settings app itself has no Configure) → Playback → Speakers (Realtek(R) Audio) (not Realtek Digital Output, the optical out) → Configure → **Quadraphonic** → Next → Finish (a stereo Windows configuration gives every driver 2 channels, and Max's `ad_mme` driver is stereo whatever Windows says); Properties → Advanced: note the format (24 bit, 48000 Hz), Enhancements: disable all; the Realtek Audio Console has the same choice (Speakers → Speaker Configuration) and gets no Speaker Fill or effects. Cables: green jack = front left and right (channels 1 and 2), black jack tip (its left) = back (channel 3)
* Max → Options → Audio Status: Driver **ad_portaudio Windows WASAPI**, Output Device **Speakers (Realtek(R) Audio)**, Sample Rate **48000** (the Windows format; Max's saved setting is 44100); I/O Mappings then lists 4 output channels. Max keeps this in its own settings, so it holds across restarts. If that driver lists 2 channels: `ad_asio` → `Realtek ASIO`, or `ad_portaudio Windows WDM-KS`. The patch plays the music on channels 1 and 2 (`ezdac~`) and the laughter on 1, 2 and 3 (`dac~ 1 2 3`: in Quadraphonic the black jack carries 3 and 4). A quick check for the back jack in Max: `cycle~ 440` → `*~ 0.1` → `dac~ 3`
* **where a laugh comes from**: the screen its grin starts on. `data\audio\screen_angles.txt` gives every screen its angle around the sphere (degrees seen from above, 0 = the camera, positive to the right), one line per screen as `index, angle;`: index = row × 6 + column of the player's grid (cell 0 top left; the Datapath unit PLn carries column n-1, its output k row k-1), + 24 for the player on 4116. The sphere has 12 ribs 30° apart, holding 5 and 3 screens in turn. The screens are numbered from the top of a 5-rib down, then the 3-rib to its **left** (seen from outside; checked on site 2026-10-25) from the top down, and so on round the sphere (1-5, 6-8, 9-13, 14-16 …), and the Datapath outputs follow that numbering: screen s is unit ⌈s/4⌉ output ((s-1) mod 4)+1, player 1's units PL1-PL6 for screens 1-24, player 2's for 25-48. So a player's grid rows 1, 2 and 3 are the heights 1, 2 and 3 of its six ribs in order (cells 6-11 are screens 2, 6, 10, 14, 18, 22) and grid row 0 holds the tops and bottoms of its three 5-ribs by turns (cells 0-5 are screens 1, 5, 9, 13, 17, 21). All of that is in `sphere.py`, which the laughter test, the scrolling name and the file follow: the file is generated from it (`python -c "from apps.smile.sphere import screen_angles_text as t; print(t(), end='')" > data\audio\screen_angles.txt`, and a test checks they agree). Only a screen's rib matters, not its height. On site: set the panel's `laughter_offset` to minus the angle of the rib the camera is in (it turns all angles at once); where the cabling differs from this, change `sphere.py`, not the file. The patch's `coll` reads it when the patch opens (plain text, no byte order mark; restart Max after a change). The speakers' own angles (-60, 60, 180) are in the three `expr`s of `p laughterSampler`, which pan each laugh over the two nearest speakers at constant power
* **laughter test** (Audio tab): `laughter_test` steps one laugh round the screens in their own order, 1 to 48 (1 to 5 down the first rib, 6 to 8 the next, and so on round), `laughter_test_step` seconds each; the screen under test is white with its number meanwhile (`laughter_test_screen` shows it too), on whatever cell the wiring puts it. The laugh must come from the numbered screen, else that screen's line in `screen_angles.txt` is wrong. It is always the same laugh, the file `laughter_test_sample` of `data\audio\laughter` (SMILE sends the patch its number in the folder's alphabetical order, case ignored, which is the order `polybuffer~ readfolder` numbers the files in on NTFS; a laugh that is not the chosen file means that order differs), at one level, and the only one: SMILE sends Max `/laughter_test 1`, which closes the gate of the clips' laughs (the laughter switch may stay as it is, the test sounds either way), and bangs Max itself with `/test_bang <index> <sample>`, past the gates. New visitors wait while the test runs

### Lights (Art-Net)
* the Art-Net node is at the panel's `artnet.ip` (10.0.0.11, universe 1); `data\artnet.json` lists the modules (`lights.py` over `modules.inout.ArtNetSender`): three cores (pc, audio, video) and the 24-LED ring around the camera (mako)

## RUN

### Start everything
* run ```apps\smile\scripts\startSMILE.bat```: it closes whatever runs of the installation (SMILE, ComfyUI, Max) and starts it all again: ComfyUI in a minimized window, Max, SMILE borderless fullscreen on its monitor with the two walls borderless on theirs
* SMILE waits for ComfyUI and shows that on its screen: the camera image in pixels with a status line (`waiting for ComfyUI`, `warming up: ...`, sharp when ready). The status line also says `no camera frames` when the camera delivers none, and the generator's reason when ComfyUI stops answering
* the apps run under `pythonw`, without a console: what SMILE says is in Poser2's `logs\`, one file per start (`smile_`), plus `crashes.log` there, one line per unhandled exception across all starts and apps; ComfyUI's logs are in `output\logs\` (`comfy_`). The first line of every SMILE log is the count: `No crashes recorded`, or `3 crashes since 2026-10-02 (logs/crashes.log), last ...`. Delete `crashes.log` to start the count over

### Settings panel
* open http://localhost:667 in a browser (also reachable from other devices on the network, the log says the address)
* presets live in `data\settings\`; `smile.json` loads at startup (the star in the panel picks the startup preset; it is kept in `data\settings\.ui_preset.json`)
* monitors are numbered primary first, then left to right: SMILE uses the one in its preset (`render.window.monitor`) and the walls the two of `render.window.secondary_list` (the first is wall 1, screens 1-24; read at the start, so restart after changing it); a wall whose monitor is not connected opens in a small window on the primary one and moves to its monitor when that is plugged in
* **Players** tab: `pool` (clips kept decoded in RAM, about 200 MB each), `recent` (the last recordings, always playing on every third of the sphere), `recycle_every`, `hwdecode` (read at the start); `fps`, `spread` and `trail` (live)

### Keys
* in the SMILE window: Enter starts a sequence, F fullscreen, W borderless fullscreen, Esc quits (the panel's Exit button does the same); fullscreen hides the mouse pointer unless the panel's window setting `fullscreen_mouse` is on (a window always shows it)
* in a wall window: Esc quits SMILE; the window setting `secondary_fullscreen` puts both walls borderless on their monitors or in a window

### Pieces on their own
* ```apps\smile\scripts\start_comfy.bat```: only ComfyUI, in this window (`--enable-manager` for the ComfyUI-Manager); the launcher does not start it, so start it first when running SMILE from VSCode
* ComfyUI log lines that are safe to ignore: `0 models unloaded.` at every sampler step (ComfyUI fills the card on purpose and reports that nothing could be freed), at startup `[ComfyUI-Manager] PyTorch is not installed` (it wants torchaudio), the `PatchTritonVAE requires triton` traceback (KJNodes, an unused node), `No module named 'llama_cpp'` (QwenVL's GGUF variant, unused), `triton not found`, `Skip loading CUDA and cuDNN DLLs since torch is imported` (a good sign: onnxruntime reuses torch's CUDA), and `ConnectionResetError ... _call_connection_lost` after "Prompt executed" (a browser tab closed). **Not ignorable**: `CUDAExecutionProvider is not in available provider names` means face analysis fell back to the CPU (crops take 25 s instead of 1 s); `install_comfy.ps1` checks the provider and reinstalls `onnxruntime-gpu` when it is missing, so run `apps\smile\scripts\install.bat` again
* ```.venv\Scripts\python launcher.py -app smile```: `-fs` borderless fullscreen with the walls borderless too (else the preset's window modes), `-wc` a webcam instead of the Vimba camera, `-lm` landscape instead of portrait, `-v` DEBUG on the console (the launcher's, before the app's)
* ```apps\smile\scripts\make_test_workflow.bat```: writes `data\comfy\smile_test.json`, the app's workflow with a preset's values plus previews and a video recorder, to drag into the ComfyUI page; it starts from the app's last capture, and any other photo goes in after ```.venv\Scripts\python -m modules.face.crop photo.jpg``` (the crop as SMILE makes it, `photo_crop.png`)
* drop a saved clip or portrait on ```apps\smile\scripts\clip_info.bat``` to see what it was made with (the record: id, style, description, seed, settings); ```.venv\Scripts\python -m apps.smile.save.record <file> --preset <name>``` writes those settings to `data\settings\<name>.json`
* tests: ```.venv\Scripts\python -m unittest discover -s apps/smile/<package>/tests -t .``` from the Poser2 root (`tests`, `face`, `comfy`, ..., `relay`)

### Output
* `output\grins\A\` and `output\grins\B\` hold the grin clips (silent h264 mp4, the walls read the style from the folder), `output\shares\` the phone's copy of each (the visitor's track as its sound, from the point the room heard when the grin started, spun up over the first half second and wound down over the last as the Max patch does, and a small watermark in the bottom right, a circled "ai" and the credit name; no caption, the joke is the room's; built before the players' copy lands), `output\portraits\` the capture and the portrait of each visitor; `output\temp\` is where they are built. About 2.9 MB per visitor, nothing is cleaned up

## SMILE ONLINE (proof of concept, branch `online`)
Someone outside gets the eye when nobody inside has it: a phone page (one camera frame with the terms over it and the bar under it), a relay that keeps the waiting line, and a link in SMILE that puts the phone's frames in place of the camera for one turn. The experience and the technical plan are the two docs in the project; `data\documents\OnlinePhone.md` is the scenario of the phone, interaction and machine, the reference the code follows; `data\documents\OnlineHosting.md` where the relay runs and how it is reached, the test on the tailnet now and the VPS later; `relay\README.md` has the relay.
* **run a test on this PC**: one line of random text in `relay\token.txt` and the same in `data\online_token.txt`; `apps\smile\scripts\start_relay.bat` (the relay on port 8800, in a window of its own: close it to stop the relay); in SMILE's panel, Online tab: `active` on (`relay` is `ws://127.0.0.1:8800/ws/smile` by default). A phone needs HTTPS for its camera: `tailscale serve --bg 8800` and open the PC's ts.net address on a phone with Tailscale, or `tailscale funnel 8800` for a phone without (switch it off after the test); the steps, and SMILE through the same proxy, are in `data\documents\OnlineHosting.md`. Without SMILE, `.venv\Scripts\python -m apps.smile.online.fake` stands in for it
* **what happens**: with `active` on, SMILE connects to the relay and tells it every second whether its eye is free (`CAMERA_SHOW` with an empty charge for `eye_free_after` seconds, the generator ready, no raw camera, no laughter test, not paused). When it is and someone waits, SMILE takes a turn: the phone's frames (640 x 800 JPEG, 15 a second) become the camera, the face finder and the charge run on them, the phone draws the judging on its own live video (no delay): the whole image in pixels as long as the face is not right, the coarser the further from good, sharp when it is, nothing drawn on it; the charge is the ring light, the page going white behind the frame as it fills (quickly at first), full white at the flash and fading with the installation's flash-out. No qualifying face within `turn_window` seconds: the turn passes (a charge that is rising gets its chance). The flash and the sequence run as for a visitor inside; from the flash to the end of the timeout the phone shows the main screen as it is rendered (`ScreenGrab` in the render, `stream_fps` frames a second at `stream_width` pixels wide, 2 a second once the result stands so the phone's download has the link; one frame in flight at a time, the phone answers each, so a slow phone gets fewer frames and never frames seconds late; the relay's log says how the frames travelled at every turn's end, JPEG over the link: the flash, the capture, the transformation, the grin with the caption, the portrait; the QR code and the operator's status line are the room's and stay out), and the turn ends with the sequence. The phone also plays the visitor's track from the flash as Max does in the room (`online.music`; SMILE uploads a track to the relay the first time it is used, as AAC, which every phone decodes where Safari refuses some MP3s; the relay keeps them), on the tape: SMILE picks the visitor's track at the turn's start and names it to the phone, which fetches and decodes it during the judging (a late one starts that far in); it plays through Web Audio (a media element goes silent at the tape's low speeds), within what a phone speaker can do (the filter never below 1.2 kHz, the tape never under 0.3, silent instead, as the patch has it); with `?debug` in the address the page shows its sound state in a corner; SMILE sends the sequence's stages with their progress and the page follows the patch's curves, the track spun up from standstill at the flash and muffled, opening up through the transformation, the turn runs through the bloom and the fade (the picture stops at the bloom; the flash-in is the phone's own image going white and the stream takes over under full white, so the room's face marks never show on the phone) and the track plays on until the phone's video is there, then winds down to a stop and the video takes over with its own sound. The phone laughs too: the room's laughter samples (uploaded once at the first connect) at random from the moment of consent, following the panel's `laughter` switch; the "I agree" tap is what unlocks the phone's sound, for both. The recording closes the moment the last grin frame is saved, while the grin still plays on the screens, and the saved portrait and grin are uploaded right then, so the phone has the video well before its turn ends; the file is downloaded once and alone, the share button appears once it is on the phone, and the phone's own clip (`output\shares\`) loops, without any caption. The phone draws and sends its camera as a mirror, so the main screen and the portrait show what the visitor saw (`online.status`, `connected`, `waiting`, `turns` are the readouts; the log says every turn)
* **the room**: an online turn takes the camera, nothing else; the main screen shows the phone's image and the sequence as always. A reset ends the turn; `active` off ends it and disconnects (the phones see `asleep`)

## KNOWN LIMITS
* no automatic restart: an app that ends by itself stays down until `startSMILE.bat` is run; `crashes.log` says what happened (the walls are part of SMILE: they go down with it)
* an app that hangs without ending is not detected either
* no messages to a phone when something fails
* SMILE Online is a proof of concept: see its section for what is not there yet
* `output\` grows about 2.9 MB per visitor; nothing is cleaned up
* on a camera path that does not pass jumbo frames the packet size stays 1500 (see the camera section)
* `data\audio\screen_angles.txt` and the scrolling name's rows assume the wiring in `sphere.py` (unit PL1 output 1 = screen 1, the top of the first 5-rib, output 2 the screen under it, unit PL2 output 1 = screen 5); check it on site (the laughter test counts 1 to 5 down the first rib, 6 to 8 down the next, and the laugh comes from the lit screen). A screen without an entry leaves its laugh where the previous one was
